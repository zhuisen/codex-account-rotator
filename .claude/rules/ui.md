- **套餐看 `plan` 不看 label**：label 只是昵称（`_autosync_live` 自动命名，现已按 plan 给 `proN`/`plusN`），但**老号从 Plus 升级到 Pro 时 label 一个字都不会变**。判套餐一律读 `slot.plan`（源自 id_token，加号时本地就解得出，无需联网）；UI 的紫色 `PRO` 徽章走 `PlanBadge`，Plus 不显示（占绝大多数，画出来只是噪音）。
- 图表曲线用 `StackedArea` 的**单调三次插值(Fritsch–Carlson)**，不是普通样条：普通样条在陡降处会过冲到基线以下，token 量画出负填充就是画了个不存在的事实，堆叠模式下还会让相邻两条带互相穿插。已用「峰后归零 / 全零突增 / 单调递增」三组数据验证采样点永不越出两端点值域。
- ★ **每层画「真带」，不是"填到基线再靠遮挡"**（2026-08-09 改）。旧画法每条 path 都填到基线、自上而下叠画，**最上层那张覆盖整个图区**；一旦 hover 让别的层降透明度，最上层的整块颜色就透出来——占 0.2% 的 Grok 看起来占满全图（用户实测截图）。`bandPath()` 用「上沿=本层累计线、下沿=前一层累计线倒序闭合」画真带；倒序那半段复用同一个插值（Fritsch–Carlson 在点序反转下对称，`dx`/`dy` 同时变号 ⇒ 斜率不变），所以公共边界逐点重合、不留缝。**旧的「堆叠带必须 `opacity:1`」那条约束是给旧画法打的补丁，已随之作废**——现在透明度和高亮才真正可用。
- **堆叠顺序：占比大的贴基线、小的压在上面**（`layers` = 自下而上的**降序**数组，浮层直接按数组序列 = 大的先读）。2026-08-09 曾按用户口头要求反成升序，**同日看到实物后用户改回**——占大头的那家铺满基线、小的作为顶上的带，比「85% 悬在半空、15% 被压在轴线上」清楚得多。**这条是看图定的，不是推理定的：改顺序前先渲染两版给用户挑。** 被 hover 的那层额外描一条上沿线：本机 Grok 只占 0.2%，带高不足 1px，光靠填充**高亮了也看不见**；降序下最小的层在最顶上，它的上沿正好是总量包络线。模型/平台配色在 `theme.ts`，必须稳定——同一模型换窗口就换色就没法读。
- **KPI 条：`space-evenly` + 每格文字居中**（用户 2026-08-09 定稿）。原来左侧紧排 + 固定 gap，右边空出一大片。用均分而不是 `justifyContent:center`——后者只是把空白从右边挪成左右各一半。首格是「总 token」，其下用**带涨绿跌红的环比**（本期 vs 等长上期；App 恒取 `--days 90`，所以 **90d 档没有上期，显示「—」**，不拿不足 90 天的一段冒充）。`合计 token` 这个旧名两页都不再用。
- ★ **`Seg` 这类控件必须定义在模块作用域**（`components/Seg.tsx`）。写在页面组件的 render 里，它每次渲染都是一个**新的组件类型**，React 会整组卸载重建：声明的 CSS transition 变成死代码，每次 hover/切档都在做 DOM 增删——表现为用户报的「点击日期档位明显卡顿掉帧」。
- ★★ **切档位的 hover 残留：唯一正确的修法是调用方传 `key={档位}`**（``<StackedArea key={`${range}:${labels[0]}`}>``；详情页是 ``${range}:${mode}:${labels[0]}`` —— 不带 `iso`，图例隔离只改图层不改日期）
  - ★ **key 必须带「数据身份」，只有档位一个字都拦不住**（2026-08-15）：`useTraffic` 每 2 分钟**原地换 labels/layers 不换实例**，而日线档窗口是「截止今天的连续 N 天」，**一过午夜整窗滑一格** —— 停着的浮层会悄悄描述另一天，索引仍在范围内，`hv` 的钳位只防越界、不防**语义过期**。用 `labels[0]` 而**不是** `labels.length`：今日档按小时**追加**，长度变但索引不移位，不该因此丢 hover。同一判据也管入场动效的依赖（`useIntro(dep)`）—— 拿 `data` 当依赖会让页面每 2 分钟自己重播，正在读的时候数字滚回 0。。组件内部清不掉，我试过两次都被用户实测推翻：
  - ✗ `useEffect(() => setHover(null), [labels.length, layers.length])` + 渲染期 `hover < n` clamp —— **不管用**。三条独立原因（codex 复核确认）：① React 复用同一实例，旧 `hover` 直接活进新数据集；② `hover` 只是个数字、不带「我属于哪一档」，切档后同一索引往往**仍在范围内**，clamp 放行——clamp 防越界，不防**语义过期**；③ `labels.length` 不是数据集 identity（不同档位可能等长、连点会跳过中间长度），且 effect 在 commit 之后才跑，新数据至少先用旧 `hover` 画一帧，排队中的旧 `mousemove` 还会写回同一个 state。
  - 反向对照实测（2026-08-09，harness 驱动 mousemove → 点 7d → 点 30d，**不发 mouseleave**）：去掉 `key` 时浮层钉在旧索引不走，30d 视图下显示 `2026-07-20`——一个从未 hover 过的日期；加回 `key` 后浮层与参考线一并消失。截图 `~/Downloads/codexbar_traffic_verify_20260809/Q_{A,B,C}_*.png`。
  - 一般规则：**只要一个组件里存着「某数据集内的索引/位置」这类 state，换数据集就用 `key` 卸载重建，别在组件内部打补丁。**
- ★ **菜单栏账号行的尾部「切换」按钮**（用户 2026-08-11 从三方案 demo 里选的 **A 覆盖式**）。
  - **点击路由**：点按钮 = 只切号；点行上**其他任何位置** = 跳主界面（既有行为不变）。按钮**必须 `stopPropagation`** —— 否则点「切换」会同时弹出主窗口，而这个按钮存在的意义正是"不用开主窗口就能换号"。
  - **绝对定位 + hover 淡入**，所以平时零占位、显隐不改布局。**当前号不给按钮**（切到自己是空操作，画出来只会让人以为点了没反应），失效号在折叠区同样不给；`onSwitch` 传不传由调用方决定，组件只管有没有。
  - 已知取舍：行右侧本来就有数据，按钮会盖住「到期」日期的尾部（当时面板 412px，2026-08-23 起为 **352px**，取舍不变）。**用户看过三方案 demo 后仍选 A**（B=每行永久留 59px，动了现有排版；C=hover 时内容左移 52px，鼠标扫过列表会连着几次滑动）。demo 留档 `~/Downloads/codexbar_menubar_switch_demo_20260811.html`。
- ★ **面板宽 `PANEL_W` 写死在三处**（`MenuBar.tsx` 常量 · `lib.rs` 的 `inner_size` · `toggle_menubar` 的居中算式），**2026-08-23 起 = 352**（用户从 412 缩窄）。不一致**不报错**，症状分两种：前端 > Rust ⇒ 弹窗左右被裁；`toggle_menubar` 对不上 ⇒ 弹窗不在托盘图标正下方。闸在 `tests/test_menubar_width_sync.py`。实测边界（真快照 + 双 Tab）：**412~332 布局干净，312 起开始折行，292 横向溢出**；下限钉 332 而不是 292，留一档余量。
- ★★ **弹窗高度 = 今日 Tab 量出来的自然高度，两个 Tab 共用**（用户 2026-09-06：「菜单栏的账号太多，高度太高了，要跟 AI 用量的高度一致」）。账号页自然高 **731px** vs 今日页，切页跳一大截，而 731 已逼近旧上限 760。今日页量出来 → `setSize` → 记进 `localStorage["codexbar_mb_h"]`；账号页用记住的值（今日页没渲染，量不到），靠 `--mb-max-h` 钳到同一个数，超出由 `.mb-list` 自己滚。
  - ★★ **同日推翻了自己的第一版：写死 `PANEL_H_MAX = 580`。** 580 是当时量到的今日页高度 —— **把一个随数据变化的量标定成了常量**。今日页高 ≈ 固定头部 + 图例行数 × 35px，图例只列**今天有流量**的平台；标定那天本机 7 家恰好 580，用户当晚只剩 4 家 ⇒ 自然高 **477**，窗口仍 580，**底部 103px 死白**（用户截图；harness `?plat=few` 复现，实测 `.mb-root` h=477 vs 窗口 580，与截图量出的空白逐像素吻合）。
    ★ 第一版的注释甚至预判了「账号很少时会留白」，却**没想到今日页自己也会变矮** —— 因为我是拿"当前这一刻的数据"去标定常量的，而那一刻恰好是最高的那种状态。**用一次观测标定常量 = 把观测当成了保证。**
  - ★★ **只有今日 Tab 能驱动高度，且必须等它有数据**（`tab === "today" && today`）。账号页一旦也去量，会按自己 656px 的内容把窗口撑回 731，正是最初要修的那个问题；不等数据则会量到 190px 的骨架，把窗口钉在下限上 —— 那是 2026-08-22「重启后弹窗只剩半截」的复活路径。
  - 记住的值必须**有界**（`PANEL_H_MIN=320` / `PANEL_H_MAX=640`）且挡 `NaN`：localStorage 里是字符串，一次异常测量会被记住、每次开机复现。
  - 已知取舍：账号池很小时账号页仍会留白。那是「切页不跳」的代价，而跳高是每次都发生的。
  - ⚠️ **旧注释里写的闸 `tests/test_menubar_tab_heights_match.py` 根本不存在**（我上一版写了个幽灵引用）。真闸是 `tests/test_menubar_panel_height.py`，其中 `ShortTodayLeavesNoDeadSpace` 用 `?plat=few` 专门守这次的死白，并先断言「夹具确实让今日页变矮了」再验空白。**指向幽灵闸的注释比没有注释更糟：它让人以为这条规则有人守着。**
  - ⚠️ **默认夹具证不了这个缺陷** —— 本机快照 7 家，今日页恰好填满，原有那组「两 Tab 等高」全绿却对死白完全沉默。同族教训见 `?agy=ok` 那条。
  - ★ **只降上限不够**：`setSize` 仍按当前页内容算，两页只是"恰好"都顶到上限；停掉一个平台后今日页就变 545（评审用 `plat=demo` 实测）。**唯一能保证一致的做法是不让它随内容变** —— 另一页没渲染，高度量不到。
  - ★★ **也不能只钳 `setSize`**：内容仍 731 高而窗口 580，`.mb-root` 是 `overflow:hidden` ⇒ 直接**裁掉**。裁切比太高更糟（内容看不见且无滚动条提示）。所以 flex 链必须**一路打通**：`.mb-root`(限高) → `.mb-pane` → `.mb-list` / `.mb-today`，每层 `min-height: 0` 都不能省。第一次只接了账号列表，今日页仍会压到底部按钮上。
  - ★ **这类缺陷三个信号一起沉默**：裁切/重叠都不算溢出，`overflow` 探针为 0、`scrollables` 为空、连「root 不许溢出」也通过。为此给 harness 加了 `scrollables` 与 `geom` 探针量 `scrollHeight vs clientHeight`。
  - `PANEL_H_MIN` **仍然需要，值从 220 提到 320**。它防的是「内容没到齐时缩成一条缝」。⚠️ 固定高度那一版曾把它删掉并写下「不存在那个状态了」——**恢复按内容测量之后那个状态就回来了**，所以它跟着回来了；真正的防线是「等今日页有数据再量」，下限只是最后一道兜底。
- ★★ **弹窗高度：`last` 必须在 `setSize` 成功之后才记账**（2026-08-22 修；⚠️ 固定高度那一版曾把它标成「不再是活跃路径」，恢复按内容测量后**它重新是活跃路径**，别再划掉）。原来是先 `last = h` 再 `setSize(...).catch(() => {})` —— 启动时窗口是 `visible(false)` 建的，这次 setSize 一旦没生效，`last` 已写成新值、内容之后不再变化 ⇒ ResizeObserver 不再触发 ⇒ 高度**永久**钉死在 `PANEL_H_MIN`。用户实测：重启后弹窗只有半截（412×232，恰好是最小高度，而内容要 596）。触发条件是**快照来得晚**（那次是 `PARSER_V` 变更让缓存作废、首扫 23s）。**另加：`menubar-shown` 时必重量一次** —— 那是唯一能保证窗口可见的时刻，不依赖 RO 是否触发。⚠️ 真因三种（RO 没触发 / 隐藏窗口 setSize 失败 / 只量了一次）**没能区分**，harness 在这件事上是抖的（同配置连跑 3 次结果不同），所以两处改动是按「在所有假说下都成立」选的。

- ★★ **单实例闸门用 `flock`，不用 `tauri-plugin-single-instance`**（2026-08-11 换掉，别换回去）。用户报「死机重启后开两个 CodexBar」，根因是**两条启动路径在开机时并发**：① autostart 插件建的 LaunchAgent（`RunAtLoad` + 直接 exec **裸二进制**）；② macOS 脏关机后由 LaunchServices 恢复。平时手点复现不出来——实测 app 已在跑时 `open -a` 会正确去重、只发 `Reopen`；但**那个去重要求第一个进程已在 LaunchServices 注册完毕**，开机时裸二进制还没注册完恢复那条 `open` 就发出去了。
  - ✗ **那个插件的闸门自己就有竞态**，而竞态恰恰是本 bug 的触发条件：它是 `connect 失败 → socket_cleanup() 删文件 → spawn 异步任务里再 bind`，两个进程同时起时 B 的 connect 早于 A 的 bind，**B 的 cleanup 把 A 刚建的 socket 删掉**，两边各自 bind 各自存活。用它压测"通过"只是没撞进那个窗口。
  - ✓ `flock(LOCK_EX | LOCK_NB)` 是内核级原子操作，两个进程同时抢**保证恰好一个拿到**；锁随 fd 由内核释放，`kill -9`/panic/断电重启都不留陈旧锁。**必须在 `tauri::Builder` 之前**，晚一步就会先把托盘和两个 webview 建出来再退出。锁文件在 app 数据目录**不在 `/tmp`**（`/tmp` 会被系统清理，文件在持锁期间被删的话新进程会在另一个 inode 上加锁，两个又都活了）。
  - ★ **三态，不是二值**：`Acquired` / `HeldByOther`(退出) / `Undetermined`(**照常启动**)。只有 `EWOULDBLOCK` 才算"被别人占"；打不开锁文件或该卷不支持 flock 一律 fail-open。**把"判定不了"和"确实被占"合并成一个值，会让 app 静默地一个都起不来**——比原 bug 严重得多。
  - 实测：flock 在本机 APFS 上 30 抢 1 恰好一个 · 真实二进制并发拉 3 个 ×3 轮均只活 1 个 · `kill -9` 后锁自动释放 · 锁文件 `chmod 000` 时照常启动。**未验：真实脏关机重启**（需重启机器）。
